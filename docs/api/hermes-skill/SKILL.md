# 家庭菜園アプリ API

## 接続情報
- ベース URL: 環境変数 `GARDEN_API_URL`（例: `http://127.0.0.1:5001/api/v1`）
- 認証: すべてのリクエストに `Authorization: Bearer $GARDEN_API_TOKEN`
- 呼び出し例: `curl -sS -H "Authorization: Bearer $GARDEN_API_TOKEN" "$GARDEN_API_URL/health"`
- レスポンスは常に `{"ok": true, "data": ...}` か `{"ok": false, "error": {"code", "message", "details"}}`

## 基本の流れ
1. 初回や選択肢が必要なときは `GET /meta` を読む（ステータス・天気・既存の種類やカテゴリ・使える関連キー）
2. 名前から ID を探す: `GET /lookup?q=<名前>`（作物・品種・場所）。植え付けは `GET /plantings?q=<作物名・品種名・場所名>`（既定は栽培中のみ）。表記ゆれ（例: サラダ菜とサラダナ）で0件になることがある。その場合は `/lookup` で作物を探し、`GET /plantings?crop_id=<id>` の結果から品種名で絞る
3. 候補が複数・0件なら、推測で決めずにユーザーに確認する（例: 「ミニトマトの植え付けが2件あります: 南の畑（5/1）とベランダ（5/3）。どちらですか？」）
4. 作成（POST）または更新（PATCH）する
5. 返ってきた `data.web_url` をユーザーに伝える

日本語を含むクエリは `curl -G "$GARDEN_API_URL/lookup" --data-urlencode 'q=ミニトマト'` のように URL エンコードする。

## 依頼の対応表
| ユーザーの依頼 | 呼ぶ API |
|---|---|
| 「アイコに花が咲いた（写真）」 | 植え付けを探す → `POST /planting_records`（`planting_id`, `recorded_at`, `notes`, `image`） |
| 「ミニトマト300g収穫」 | 植え付けを探す → `POST /harvests`（`planting_id`, `harvest_date`, `quantity: 300`, `unit: "g"`、写真があれば `image`） |
| 「トマトサラダを作った」 | `POST /cooking_records`（`title`, `cooked_date`、当日の収穫があれば `relations.harvest_ids`） |
| 「明日追肥する」 | `POST /tasks`（`title`, `due_date` は今日の日付から計算、植え付けが分かれば `relations.planting_ids`） |
| 「今日の畑日記」 | `POST /diary_entries`（`title`, `entry_date`, `content`, `weather`） |
| 「アイコの栽培を終わりにした」 | 植え付けを探す → `POST /plantings/{id}/end` |
| 「ベランダにバジルを植えた」 | `/lookup` で作物・場所を探す → `POST /plantings`（`location_id` と、`crop_id` か `variety_id` の**どちらか一方**） |
| タスクが終わった | `PATCH /tasks/{id}` に `{"status": "completed"}` |
| 登録済みのデータに写真を付けたい | `PATCH /{種類}/{id}` に `-F image=@...`（`data` は省略可）。既存の画像は置き換わるので、ある場合はユーザーに確認し、残すなら `extra_images` で追加する |
| 「新しい作物○○を登録して（写真）」 | `GET /meta` の `crop_types`（既存の種類）から `crop_type` を選ぶ（**必須**。合うものが無ければユーザーに確認）→ `POST /crops`（`name`, `crop_type`、写真は `image`、`notes` は下の「作物・品種のメモの書き方」）→ **続けて Web ページと YouTube 動画を補足情報に付ける**（下の「参考情報の集め方」の 1） |
| 「新しい品種○○を登録して（写真）」 | `/lookup?q=<作物名>` で作物 ID を探す（作物がなければ先にユーザーに確認）→ `POST /varieties`（`name`, `crop_id`、写真は `image`、`notes` は下の「作物・品種のメモの書き方」）→ **続けて Web ページと YouTube 動画を補足情報に付ける**（下の「参考情報の集め方」の 1） |
| 品種のメモ・補足写真 | `PATCH /varieties/{id}` に `{"notes": "..."}`。補足の写真は `-F extra_images=@...`（返却の `extra_images` に `supplement_id` が付く） |
| 写真が複数枚 | 1枚目を `image`、残りを `extra_images`。栽培記録は1件1枚なので、枚数分の記録を作るかユーザーに確認 |
| 参考ページの URL を残したい | `PATCH /{種類}/{id}` に `{"extra_urls": ["https://..."]}`（作成時の POST にも入れられる）。補足情報（URL）として追加され、ページのタイトルは自動で取得される。同じ URL は二重に追加されない。植え付け・栽培記録には付けられない |
| 参考になる YouTube 動画を残したい | `PATCH /{種類}/{id}` に `{"extra_youtube": ["https://www.youtube.com/watch?v=..."]}`。補足情報（YouTube）として追加され、アプリの画面に動画が埋め込まれる。動画のタイトルはアプリが YouTube から取得する。同じ動画は二重に追加されない。付けられる種類は `extra_urls` と同じ |
| 「アイコの参考になる情報を集めてきて」 | 下の「参考情報の集め方」の 2 |
| 「アイコの生育状況を見て」「最近の様子どう？」 | 下の「生育状況の診断」の手順 |
| 写真だけ先に送られた | `POST /photos` でプールに上げ、後で `photo_pool_id` / `extra_photo_pool_ids` で使う |

## 作物・品種のメモの書き方
作物（`POST /crops`）・品種（`POST /varieties`）を新しく登録するとき、メモについてユーザーの指示がなければ、`notes` に次の形式の栽培メモを書いて一緒に登録する（アプリ画面の「AIで下書き」と同じ形式）。ユーザーがメモの内容を指示したときはそれに従う。既存の作物・品種のメモは、頼まれない限り書き換えない。

- 時期は `GET /meta` の `region`（地域・栽培環境）を基準に書き、冒頭に「（{region}基準）」と添える。空なら「（一般的な目安）」と添える。種まきと苗の植え付けを区別する
- 品種なら、親作物の一般論ではなく、その品種固有の特徴（味・サイズ・耐病性・草勢など）を優先する
- **確かでない情報は推測で書かず「情報なし」と書く**。知らない品種の特徴をもっともらしく作らない（Web 検索が使えるなら調べてから書く）
- Web 検索で調べたときは、末尾に `## 参考URL` を付けて見たページの URL を箇条書きにする（3件程度、多くても5件）。調べていなければ付けない
- `## 参考URL` はメモの根拠なので、地域のページが入ってよい。補足情報（`extra_urls`）には写さない（補足情報は地域を入れずに別に調べる。下の「参考情報の集め方」）
- 登録できたら、続けて Web ページと YouTube 動画を補足情報に付ける（下の「参考情報の集め方」の 1）
- 登録後の返答で「メモは AI の下書きです。違っていたら画面から直してください」と添える

```markdown
## 植え付け時期
（○○基準）
- 種まき: ○月〜○月（育苗）
- 苗の植え付け: ○月〜○月

## 収穫時期
- ○月〜○月

## 特性
- ...

## 栽培のコツ
- 株間:
- 水やり:
- 肥料:
- 病害虫:
- コンパニオンプランツ:
```

## 参考情報の集め方
育て方を勉強するための Web ページと YouTube 動画を、作物・品種の補足情報に付ける。良いかどうかはユーザーが見て決めるので、Hermes は候補を付けるところまで。

1. **作物・品種を新しく登録したとき（毎回、頼まれなくても行う。登録の返答をする前に必ず済ませる）**
   - 登録の POST が成功してから、Web ページと YouTube 動画をそれぞれ3件程度（多くても5件）探し、`PATCH /{crops か varieties}/{id}` に `{"extra_urls": [...], "extra_youtube": [...]}` で付ける。登録の POST には入れない（1件が 422 になると作物・品種の登録まで失敗するため）
2. **登録済みの作物・品種に「参考になる情報を集めてきて」と頼まれたとき**
   - `GET /{crops か varieties}/{id}` で、既に付いている `extra_urls` と `extra_youtube` を確かめる
   - まだ付いていない Web ページと YouTube 動画を、それぞれ3件程度（多くても5件）探す
   - `PATCH /{crops か varieties}/{id}` に `{"extra_urls": [...], "extra_youtube": [...]}` で付ける。補足情報を足すだけで既存の内容は変わらないので、対象が1件に決まればユーザーに確認せず追加してよい
   - **メモ（`notes`）は書き換えない**
- 探し方: **地域（`/meta` の `region`）や地名を検索語に入れない**。「○○ 育て方」「○○ 栽培 コツ」のように一般的な育て方で探し、特定の地域向けのページ・動画は選ばない（地域に合わせた時期はメモのほうに書く）
- 選び方: 品種なら、その品種を直接扱うものを優先し、足りなければ作物全般の育て方（植え付け・脇芽かき・追肥・病害虫など）で補う。家庭菜園向けのものを選び、同じ内容の重複は避ける
- 動画は**検索結果に実際に出てきた URL だけ**を使う。URL を推測で作らない（アプリが YouTube に動画の有無を問い合わせ、無い動画は 422 になる）
- `extra_youtube[i]` が 422 になったら、その動画を外して残りを1回だけ送り直す
- 返答では、付けたもののタイトルを一覧で伝え、`web_url`（画面の補足情報で見られる）を添える。見つからなければそう伝える。作物・品種の登録の返答に YouTube のことが書かれていなければ、手順を飛ばしている

## 生育状況の診断
登録済みの栽培記録の写真から生育状況を答える手順。`image_url` は Web 画面の URL で開けないので、画像は必ず API の `GET /{種類}/{id}/image` で保存してから見る。

1. 植え付けを特定する（「基本の流れ」と同じ。候補が複数ならユーザーに確認）
2. `GET /planting_records?planting_id=<id>&limit=10` で記録を新しい順に取り、`image_url` が `null` でないものから**最新**と**その前の1件**を選ぶ（前回が無ければ最新だけ）
3. 画像を保存する
   - 最新（元画像）: `curl -sS -H "Authorization: Bearer $GARDEN_API_TOKEN" -o /tmp/garden_latest.jpg "$GARDEN_API_URL/planting_records/<最新のid>/image"`
   - 前回（サムネイル）: 同様に `"$GARDEN_API_URL/planting_records/<前回のid>/image?size=thumb"` を `-o /tmp/garden_prev.jpg` で保存
4. `vision_analyze` で両方の画像を見る。**画像を見ずに生育状況を答えない**（見られなかったらそう伝える）
5. 次をまとめて答える
   - 最新の記録日・植え付けからの日数（`days_from_planting`）・記録のメモ
   - 写真から分かること（葉の色・茂り方・花や実の有無・しおれ・斑点や食害の跡など）
   - 前回の記録日と比べた変化（前回が無ければ省く）
   - 気になる点があれば対処の候補。病害虫は写真1枚で断定せず「〜の可能性があります」とし、確かめ方（葉の裏を見る、など）を添える
6. 画像付きの記録が1件も無ければ、写真を送ってもらうよう伝える（送られたら栽培記録として登録してから診断する）

- 他の種類の画像も同じ形で取れる（`/crops/{id}/image` など、写真プールは `/photos/{id}/image`）。404 の `no_image` は画像が未登録
- 診断の結果は、頼まれない限り記録や日記に書き込まない

## 送り方
- JSON: `-H 'Content-Type: application/json' -d '{...}'`
- 写真付き: `-F 'data={...JSON...}' -F image=@/path/to/photo.jpg -F extra_images=@/path/2.jpg`
- 写真を付けられる種類: `image`（本体画像1枚）は作物・品種・場所・栽培記録・収穫・料理・日記。`extra_images`（追加画像）は栽培記録・植え付け以外のすべて（タスクは `extra_images` だけ）。**ユーザーが写真を送ってきたら、依頼された登録に必ず添付する**（付けられるか分からないときは推測で諦めず、そのまま送って 422 の内容を見る）
- 写真のパーツ名: `POST /photos` だけは `-F files=@...`。それ以外は `image` / `extra_images`（パーツ名を間違えると 422）
- multipart の `data` は**ファイルではなく値**。JSON 文字列を `-F "data=$(cat body.json)"` のように渡す（`-F data=@body.json` は 422）
- 省略できる項目は送らない（収穫の `quantity` / `unit`、日記の `weather` など。分からない値を推測で埋めない）
- 日付は `YYYY-MM-DD`。数値に単位を付けない（`"quantity": 300, "unit": "g"`）
- PATCH は変えたい項目だけ送る。`relations` は送ったキーだけ置き換わる（`[]` で全解除、送らないキーはそのまま）
- 品種として植えた植え付けを探すときは、作物 ID で絞り込むと品種経由のものも含まれる（`GET /plantings?crop_id=1`）

## コマンドの実行
- API は `curl` だけで呼ぶ。レスポンスの JSON は**そのまま読んで**、必要な値（ID・名前・日付など）を自分で拾う
- `python3 -c`・`python3 -` などのスクリプトや、`jq` へのパイプで整形・集計しない（実行のたびにユーザーの承認が必要になる）
- レスポンスが長いときは、スクリプトではなく API の条件で絞る（`q`、`crop_id`、`date_from`、`limit` など）
- 一覧は既定で50件まで。件数を答えるときや全件が必要なときは `meta.total` を見て、`data` の件数より多ければ `limit=200` や `offset` で残りも取得する（`data` の件数を総数として答えない）
- ユーザーへの返答は、読んだ内容を自分の言葉でまとめる（表や一覧を作るためにコマンドを使わない）

## 守ること
- **削除はできない**。削除を頼まれたら「API では削除できないので、アプリの画面から操作してください」と伝え、`web_url` を示す
- PATCH の前に、対象（名前・日付・ID）をユーザーに確認する
- 「昨日」「今日」などは、その都度 `date +%F` で今日の日付を確かめて実際の日付に変換し、返答でも日付を明記する（過去の会話や記憶にある日付を使わない）
- 音声入力の文字は誤変換されやすい（品種名が意味の通らない語になるなど）。対象が決まらないときは候補を挙げて確認し、意味の分からない語を登録名に使わない
- 写真から作物・品種を判断するときは、必ず画像を見て確認する（`vision_analyze` など）。画像を見ずに作物名を答えたり登録したりしない。品種名が読み取れなければ、作物名で登録するかユーザーに聞く
- 写真に複数の植え付けが写っていて、対象が一部しか確定しないときは、確定したものから登録し、残りは候補を示して確認する
- 日記などの文章に、店名など確証のない固有名詞を書かない（ユーザーに確認する）
- 422 が返ったら `error.details` の `field` と `reason` を読んで直し、再送は1回まで。直せなければユーザーに内容を伝える
- 接続できない（タイムアウト・接続拒否）ときは再送せず、「菜園アプリのサーバー（garden-app.service）が止まっている可能性があります」と伝える
- POST がタイムアウトしたときは、同じ内容を再送する前に一覧（例: `GET /harvests?date_from=<今日>`）で登録済みか確認する（二重登録防止）
- 栽培記録・収穫は**栽培中の植え付けにだけ**作成できる（終了済みは 422）。栽培中の植え付けが見つからなければ、終了済みの植え付けを候補に出さず「栽培中の植え付けがありません。先に植え付けを登録しますか？」と伝える
- 415 の場合や、送られた画像ファイルを読めなかった場合（iPhone の写真を「ファイル」で送ると HEIC になり、受け取りの時点で読めない）は、「ファイル」ではなく「写真」として送り直してもらう
- トークンをユーザーへの返答やログに出さない
