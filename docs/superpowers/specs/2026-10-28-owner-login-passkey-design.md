# 自分だけが編集できるようにする（パスキーでログイン）設計

- 作成: 2026-10-28
- 段階: 段階5「アプリから Hermes へ依頼を出せるようにする」の前提となる作業1（作業2 = Hermes への依頼画面は、これが済んでから別に設計する）

## 目的と背景

PC でアプリを見ているときに浮かんだ疑問（「玉ねぎはそろそろ植え付けか」「大豆の収穫はまだか」など）を、Element X に持ち替えずにアプリの画面から Hermes に聞きたい。Element X と同じく登録・編集の依頼もできるようにしたい（作業2）。

ところが今のアプリには認証が無く、LAN 内の誰でも登録・編集・削除ができる。この状態で Hermes への依頼画面を作ると、家族の端末からも Hermes（ターミナルを使える）に指示を出せてしまう。そこで先に、**登録・編集・削除と（作業2の）Hermes への指示を自分だけに限る**仕組みをアプリ全体に入れる。

ログインは、パスワードではなく**パスキー**（PC は Windows Hello の顔認証、iPhone・iPad は Face ID）にする。ユーザーは PC に顔認証でログインしていて「楽で安全」と感じており、同じ体験を望んだ。

## 決まったこと（ユーザーが決めた）

- 利用者は2種類。**自分**（ログインすると登録・編集・削除・写真プールへのアップロード・AI 下書き・作業2の Hermes への依頼ができる）と、**家族**（ログインなし。閲覧だけ）
- 家族はログインなしで、今までどおり**どの画面も見てよい**（Hermes との会話の履歴・設定画面も含む）。見せたくない画面は無い
- 端末は家族と共用しない（全員が別々の端末）。自分の端末では一度ログインしたら長く保ってよい
- 守る対象はアプリの Web 画面全体。Hermes 用の API（Bearer トークン）と Matrix は、すでに別の鍵で守られているので対象外
- ログインはパスキー
- 名前は **`<サーバーのホスト名>.local`（mDNS、サーバーの avahi）** を使う。理由: **LLM 以外はクローズドであってほしい**（外部の名前サービス sslip.io や、自分のドメインの DNS に頼らない）
- 入口を2つに分ける
  - `http://<サーバーのIP>:5000`（今の URL）: **誰にとっても閲覧専用**。自分もここでは編集しない。家族の端末は証明書を入れなくてよい
  - `https://<サーバーのホスト名>.local/`（新しい URL）: パスキーでログインして、登録・編集（作業2では Hermes への依頼も）をする入口。自分の PC・iPhone・iPad で使う
- 家族が HTTPS の URL を開いた場合: 証明書の警告が出る。警告を無視して進めても、ログインしていない人として閲覧だけができる。家族の端末にはパスキーが無く、新しいパスキーの登録はログイン済みの人だけができるので、ログインはできない

## 試作で確かめたこと（2026-10-28）

使い捨ての試作（Flask + py_webauthn 3.0.1、登録・ログインのボタンだけの画面）で確かめた。試作のコードと、サーバーに一時的に足した設定はすべて片付け済み。

| 確かめたこと | 結果 |
|---|---|
| py_webauthn（cryptography 50.0.2・cbor2・pyOpenSSL を引き込む）が、メイン PC の Smart App Control に止められないか | 止められない。import と鍵の生成まで通った |
| メイン PC で `http://localhost`（RP ID `localhost`）のまま、Windows Hello の顔認証で登録・ログインできるか | できた（開発環境は HTTPS 不要） |
| サーバーに avahi を入れ、PC・iPhone・iPad から `<サーバーのホスト名>.local` を引けるか | PC・iPhone は引けた。iPad は下記 |
| Caddy（`tls internal`、Matrix と同じ自前の発行元）で `https://<サーバーのホスト名>.local:<試作のポート>` を出し、パスキーで登録・ログインできるか | PC（Chrome、Windows Hello）・iPhone（Safari、Face ID）とも登録・ログインできた。iPad（Safari）は iPhone で登録したパスキーが iCloud キーチェーンで同期され、登録なしでログインできた |
| サーバーの Python（3.14、uv 版ではない素の Python）で py_webauthn を入れて動くか | 動いた（本番のアプリは uv の Python なので、そちらでも `uv sync` で確かめる） |

分かった制約:

- **iPad mini（第5世代）は、Wi-Fi の「セキュリティ Wi-Fi」の SSID（AP モードのエレコムのルーター）では `.local` を引けない**。サーバーの mDNS の答え（マルチキャスト）が iPad に届かない（tcpdump で、iPad が問い合わせを繰り返し、サーバーが答えているのを確認）。5G の SSID なら引ける。運用で対処する: iPad でログインして編集するときは 5G の SSID につなぐ（ふだんの接続先を 5G にしてもよい）。**本番の作業（2026-10-28）では iPhone も同じく登録用の URL を開けなかった**ので、iPhone・iPad ともふだんの接続先を 5G の SSID にした。閲覧は IP の HTTP で今までどおりできる
- 登録されたパスキーは、どの端末でも `backed_up: true`（端末をまたいで同期されるパスキー）だった。仕組みはこれを前提にしてよい（同期されないパスキーも受け付ける）
- PC は Caddy の発行元の証明書を「現在のユーザーの信頼されたルート」に入れた（2026-10-28、SHA-256 を照合済み）。iPhone・iPad は Matrix のときに入れてある

## ゴール

1. ログインしていない人は、HTTP・HTTPS のどちらからでも**閲覧だけ**ができる。登録・編集・削除・アップロード・AI 下書き・見取り図の保存など、データや外部への課金に関わる操作は**サーバー側で拒否する**
2. 自分は `https://<サーバーのホスト名>.local/` でパスキーでログインし、今までどおりのすべての操作ができる。ログインは 180 日保つ
3. 画面上は、ログインしていない人には登録・編集・削除のボタンやフォームへの入口を出さない
4. 全部の端末をなくしても、サーバーで自分だけが実行できるコマンドからやり直せる（非常口）
5. Hermes の実行ユーザーは、新しい HTTPS の入口を経由しても Web 画面に届かない（今の「5000番への接続を拒否」と同じ水準を保つ）

## やらないこと

- 家族ごとのアカウント、権限の細かい段階（「家族は日記だけ書ける」など）
- パスワードでのログイン（パスキーだけ）
- 家族の端末を HTTPS にすること（家族は HTTP のまま）
- 外部の名前サービス・自分のドメイン・Let's Encrypt
- iPad のセキュリティ Wi-Fi で `.local` を引けるようにするための、ルーターの設定変更
- Hermes 用の API（`create_api_app`、Bearer トークン）の認証の変更
- 作業2（Hermes への依頼画面）

## 失敗とみなすこと（動いても不可）

- 家族の閲覧が今までより不便になる（HTTP の URL が変わる、証明書の警告が出る、閲覧にログインが要る）
- ログインしていなくても、どこか1か所でもデータを変えられる（ボタンを隠しただけで、POST を直接送れば通る、など）
- Hermes の実行ユーザーが Caddy の新しい入口を経由して Web 画面に届く
- LLM 以外の外部サービスに頼るようになる（CDN の新規追加も含む）
- 非常口が無く、端末をなくすと自分も編集できなくなる
- Hermes 用の API や、会話の取り込み（`tools/hermes_conversation_sync.py` → API）が動かなくなる

## 全体の構成

```
家族の端末 ──HTTP──▶ <サーバーのIP>:5000 ─────────────▶ waitress（Web アプリ）  閲覧専用（セッションの Cookie は届かない）
自分の端末 ──HTTPS─▶ <サーバーのホスト名>.local:443 ─▶ Caddy ─▶ 127.0.0.1:5000  パスキーでログイン → 編集
Hermes ──────────────────────────────────────────────▶ 127.0.0.1:5001（API、今までどおり）
Hermes ──✕──▶ 5000 番（既存の ufw のルール）／ ──✕──▶ Caddy の 443 番（今回足すルール）
```

- 名前: サーバーの avahi（2026-10-28 に導入済み。下記「サーバー側」）
- 証明書: Caddy の `tls internal`（Matrix と同じ自前の発行元）
- Caddy から Web アプリへは `127.0.0.1:5000` に転送する（Web アプリは今までどおり 5000 番だけで待ち受ける。ポートを増やさない）

## アプリの振る舞い

### 「ログインしている」の判定

- Flask のセッション（署名付き Cookie）に「ログイン済み」の印を持つ。ログイン時に `session.permanent = True`、有効期限は 180 日
- **本番ではセッションの Cookie に `Secure` を付ける**。HTTP の入口（5000 番、IP でも `http://<サーバーのホスト名>.local:5000` でも）には Cookie が送られないので、HTTP からは常に「ログインしていない人」になる。これで「HTTP は誰にとっても閲覧専用」が自然に成り立つ。`HttpOnly`・`SameSite=Lax` も付ける
- 開発環境（`run.py`、`http://localhost:5000`）では `Secure` を付けない。Chrome は localhost の Secure の Cookie も受け付けるが、設定で切り替えられるようにしておく
- ログインしていない HTTP の画面では `flash()`（セッションに入る）が次の画面に残らなくなる。家族は送信をしないので受け入れる

### サーバー側の拒否（一番大事）

- **既定で拒否**: Web アプリ（`create_app`）の `before_request` で、「GET・HEAD・OPTIONS 以外のリクエストは、ログインしていなければ拒否する」を一括で行う。個々のルートに付け忘れても漏れない。例外はログイン・パスキーの処理に必要な POST だけ（明示した許可リスト）
- 拒否したときの応答: 画面のフォームの送信なら、ログイン画面へ案内する（HTTPS なら移動、HTTP なら「編集は `https://<サーバーのホスト名>.local/` で」の案内）。JS の `fetch` には JSON の 401/403 を返す（既存の JS の作法に合わせる）
- **GET でも、編集のための画面（新規・編集フォーム、写真の振り分け、一括登録、見取り図の編集など）は、ログインしていなければ同じく案内する**。どの GET ルートが編集用かは、エンドポイントの一覧を出して漏れなく決める（`create_app('testing')` の `url_map`。`docs/dev-workflow-tips.md` の「ドキュメントとコードの照合」）
- GET なのにデータを変える・外部へ接続する・課金するルートが無いかも調べる。あれば POST に直すか、上の「編集用」に入れる
- Hermes 用の API（`create_api_app`）にはこの仕組みを入れない

### CSRF 対策

- セッションに CSRF トークンを持ち、**ログイン中の**すべての POST（など）でフォームの隠し項目またはヘッダー（`X-CSRFToken`）と照合する。合わなければ 400
- テンプレートはベースのレイアウトの `<meta>` にトークンを置き、各フォームに隠し項目を入れる。JS の `fetch`（見取り図の保存、AI 下書き、写真の振り分けなど）は `<meta>` から読んでヘッダーに付ける。すべてのフォーム・`fetch` に付いているかは、テストで「トークン無しの POST は拒否される」と「画面から出した POST は通る」の両方を確かめる
- Flask-WTF は使わない（このアプリは WTForms を使っておらず、必要なのはトークンの発行と照合だけ）

### 画面

- ナビの右端に「ログイン」（ログインしていないとき）／「ログアウト」（ログイン中）。HTTP の入口で「ログイン」を押すと HTTPS の URL へ移る
- ログイン画面: 「パスキーでログイン」のボタン1つ。ユーザー名の入力は無い（端末に保存されたパスキーを選ばせる。試作と同じ `allow_credentials` 空の方式）
- ログインしていない人には、登録・編集・削除・アップロード・AI 下書き・「写真プールから選択」などのボタンと、新規作成への入口を出さない（Jinja のグローバル、例えば `is_owner` で分ける）
- 設定画面に「パスキー」の欄: 登録済みのパスキーの一覧（名前・登録日・最後に使った日）、名前の変更、削除、「この端末のパスキーを追加」（ログイン中だけ）。最後の1つを消すときは確認する

### パスキー

- 依存は `webauthn`（py_webauthn）。試作では 3.0.1 で動いた。版は計画の段階で固定する
- RP ID と origin は `.env` で設定する（例: `PASSKEY_RP_ID=<サーバーのホスト名>.local`、`PASSKEY_ORIGIN=https://<サーバーのホスト名>.local`）。開発環境の既定は `localhost` / `http://localhost:5000`
- 登録: `resident_key=REQUIRED`、`user_verification=REQUIRED`、`attestation=none`。既存のパスキーは `exclude_credentials` に入れる。利用者は1人なので `user_id` は固定
- ログイン: `user_verification=REQUIRED`、検証で `require_user_verification=True`。`sign_count` を保存して更新する（同期されるパスキーは 0 のままのことがある。0 のときは増えなくても拒否しない。py_webauthn の既定の振る舞いに従う）
- チャレンジはセッションに一時的に置き、検証したら消す
- 保存先: 新しい表（例 `passkeys`: 資格情報 ID（一意）、公開鍵、sign_count、名前、登録日時、最後に使った日時）。マイグレーションで足す
- ログイン後は、セッションを作り直して（固定化対策）ログイン済みの印を入れる
- **ログインの取り消し（端末をなくしたとき）**（Claude の判断）: セッションには「どのパスキーでログインしたか」（パスキーの表の ID）を入れ、リクエストごとにそのパスキーが DB に残っているかを確かめる。設定画面でパスキーを消せば、そのパスキーで入った端末のログインはすぐ切れる。署名付き Cookie だけでは発行済みのログインを取り消せない（180 日有効のまま）ため。全部の端末をなくして非常口を使ったときは、古いパスキーを全部消せば、全部のログインが切れる

### 非常口（最初の1つ目と、全部の端末をなくしたとき）

- サーバーで実行する Flask のコマンド（例 `uv run flask --app app passkey-register-link`）が、**1回限り・期限付き（例 15 分）の登録用 URL** を表示する。その URL を開くと、ログインしていなくても1回だけパスキーを登録でき、そのままログイン済みになる
- トークンはサーバーのプロセスとコマンドの間で共有するので DB に置く（ハッシュで保存し、使ったら消す）
- サーバーにログインしてこのコマンドを実行できるのは自分だけ。何に支えられているか:
  - コマンドは `sudo -u garden -H ...` で `garden` ユーザーとして実行する（`/opt/garden-app` と DB は `garden` のもので、Hermes の実行ユーザーは触れない）
  - Hermes はログイン用のユーザー（sudo できるユーザー）のユーザー systemd で動いている。ただし sudo には**パスワードが必要**（2026-10-28 の作業でも毎回聞かれた）。Ubuntu の既定ではパスワードの記憶は端末（tty）ごとなので、自分が SSH で sudo した直後でも、Hermes のプロセスはそれを使い回せない
  - したがって、**パスワードなしの sudo（`NOPASSWD`）を設定しない、sudo の記憶を端末ごとから変えない**ことが前提。計画の中で `sudo -l` と `/etc/sudoers.d/` を読み取りで確かめる手順を入れる
  - 仮に Hermes が URL を手に入れても、Hermes の実行ユーザーは 443 番に届かない（下記「Hermes の遮断」）

## サーバー側

- **avahi**（2026-10-28 に導入済み）: `avahi-daemon` を apt で入れた。`/etc/avahi/avahi-daemon.conf` は `disable-user-service-publishing=yes`（一般ユーザー＝Hermes の実行ユーザーが LAN に名前を流すのを禁止）、`use-ipv6=no`、`publish-aaaa-on-ipv4=no`（ufw は IPv4 の LAN だけ許可しているため）。元の設定は `avahi-daemon.conf.orig`。ufw で `<LANの範囲>` から UDP 5353 を許可済み
- **Caddy**: `https://<サーバーのホスト名>.local` のサイトを足し、`tls internal` で `127.0.0.1:5000` に転送する。Caddy が付ける `X-Forwarded-Proto` などを信用するのは Caddy（127.0.0.1）からだけにする（Werkzeug の `ProxyFix` など）。ufw で `<LANの範囲>` から 443 番を許可する
- **Hermes の遮断**: `before.rules` / `before6.rules` の `-o lo -j ACCEPT` の直前に、Hermes の実行ユーザーから 443 番（Caddy のアプリの入口）への接続を拒否するルールを足す（既存の 5000 番のルールの置き場所にならう。`docs/api/migration-to-ubuntu.md` の手順 6）。**既存の 5000 番のルールは宛先を絞っていないが、443 番で同じことをすると Hermes のインターネットへの HTTPS（ChatGPT・OpenRouter・Web 検索）が全部止まる。必ず `-o lo` を付けて自分のサーバー宛てだけを止める**（自分の LAN IP 宛ても `lo` を通るので、これで足りる）。Hermes の実行ユーザーで外部の HTTPS（例 `curl -sI https://example.com`）が通ることも確かめる。Hermes の実行ユーザーで `curl https://<サーバーのホスト名>.local/` と `curl -k https://127.0.0.1/` が拒否されることを確かめる。Matrix の 8448 番は止めない（Hermes は Matrix に `127.0.0.1:8008` で直接つないでいて、8448 番には触れない。8448 番の Caddy は Tuwunel にしか転送しない）
- **`SECRET_KEY`**: サーバーの `.env` に固定の値があるかを確かめる（無いと再起動のたびにログインが外れる。`create_app` は未設定なら起動ごとのランダム値で補う）。無ければ作る
- **`.env` に足す値**: `PASSKEY_RP_ID`、`PASSKEY_ORIGIN`、（必要なら）`SESSION_COOKIE_SECURE`
- **`WEB_BASE_URL` を HTTPS に変える**（ユーザーが決めた）: `WEB_BASE_URL=https://<サーバーのホスト名>.local`。API の応答の `web_url` など、Hermes が Matrix の返事に付けるリンクが HTTPS の入口になり、ログイン済みならそのまま編集できる。Hermes の返事を読むのはほぼ自分だけなので家族への影響は無い（iPad がセキュリティ Wi-Fi のときはリンクが開けないことを受け入れる）。あわせて、`hermes-skill/SKILL.md` の URL の記述、会話の取り込み・リンクの解析（`app/utils/conversation_links.py`）が URL の形（`http://…:5000`）に頼っていないかを確かめ、頼っていれば両方の形を受け付ける（取り込み済みの会話には古い形のリンクが残っている）。`WEB_BASE_URL` を使う箇所は `grep` で洗い出す

## 開発とテスト

- 開発: `run.py`（`http://localhost:5000`）のまま、RP ID `localhost` で Windows Hello のパスキーを登録・ログインできる（試作で確認済み）。コピー DB での確認は `docs/dev-workflow-tips.md` の手順
- 自動テスト: py_webauthn の `verify_registration_response` / `verify_authentication_response` は差し替える（実物の認証器は使えない）。差し替えの引数名は `inspect.signature` で実物と照合する
- テストで確かめる主な点
  - ログインしていないと、すべての POST（など）が拒否される（URL の一覧から機械的に全部試す）
  - ログインしていないと、編集用の GET が案内に回る。閲覧用の GET は今までどおり 200
  - ログイン中でも、CSRF トークンの無い POST は拒否される
  - 非常口の URL は1回だけ・期限内だけ使える
  - API アプリ（`create_api_app`）は影響を受けない
- 既存のテストは、多くが POST をそのまま送っている。テスト用に「ログイン済み＋CSRF を通す」フィクスチャを用意して、既存のテストを書き換えずに済むようにする（作り手の判断）

## 進め方（段階の案）

1. **アプリの土台**: ログイン（パスキー）、非常口のコマンド、既定で拒否、CSRF、ログイン・ログアウトの画面、設定画面のパスキーの欄、テスト
2. **画面の出し分け**: ログインしていない人には編集のボタン・入口を出さない（テンプレート約30ファイル）
3. **サーバー**: Caddy のサイト、ufw（443 番の許可と Hermes の拒否）、`.env`、PR のブランチで動作確認（家族の閲覧が変わらないこと、PC・iPhone・iPad でログインできること、Hermes から届かないこと）→ マージ → main に戻す
4. **文書**: ルート `CLAUDE.md`（「認証なし」の記述）、`app/routes/CLAUDE.md`（新しいルートの規約: 既定で拒否・編集用 GET の扱い・CSRF）、`docs/api/migration-to-ubuntu.md`（avahi・Caddy・443 番の遮断）、`docs/api/hermes-local-chat.md`（Caddy の設定が増えたこと）、`README.md`、`app/models/CLAUDE.md`（新しい表）
