# Hermes との会話の履歴 設計

- 作成: 2026-10-26
- 対応する wishlist: 「Hermes との会話の履歴をアプリで見られるようにする」（段階5）。「Hermes のアドバイスを植え付けの画面で見られるようにする」の案(1)（会話から関係するデータを自動で結び付ける）もこの設計で満たす

## 目的と背景

Hermes には Element X（Matrix）から記録の登録や相談を頼んでいる。会話は自動リセットで毎朝（と6時間あいたとき）区切られ、Element X の部屋を遡らないと過去のやりとりを探せない。

ユーザーがアプリの画面を見ている途中で、次のように思ったときに、アプリの中で確かめられるようにする。

- 「何日か前に Hermes に記録を頼んだっけ？」 → 依頼の文と、Hermes が実際に作った・変えたデータが分かればよい
- 「ちょっと前に相談したけど、回答は何だった？」 → 自分の質問と Hermes の返事が読めればよい

探し方は2通りとも使う（ユーザーの回答）: 専用の会話の一覧からたどる／植え付けなどの詳細画面から、そのデータが出てきた会話を開く。

## ゴール

1. 専用の一覧ページ（新しい順、日付とキーワードで絞り込み）と会話の詳細ページ
2. 会話の詳細は、ユーザーの発言と Hermes の返事の文章だけを表示する。写真付きの発言には縮小版の写真を出す（届いていない写真は「写真あり」）。Hermes が作った・変えた・見たデータへのリンクを並べる
3. 各データの詳細画面に「このデータが出てきた Hermes との会話」（日付・題名・区分）を出し、会話の詳細へリンクする
4. サーバーの Hermes の実行ユーザーで動くスクリプトが、systemd のタイマーで定期的に `~/.hermes/state.db` を読み、アプリの API に会話を送る（データの流れは Hermes → API だけ）
5. 最初の取り込みで、既存の Matrix の会話（2026-10-18 以降、2026-10-26 時点で12件）も入る

## やらないこと（今回）

- Matrix 以外の会話（`cli` / `oneshot` / 停止した `telegram`、サブエージェント・cron）は取り込まない（ユーザーの回答）
- アプリから会話を消す・直す機能は作らない。Hermes 側で会話が消えてもアプリには残し続ける（ユーザーの回答）
- アプリから Hermes へ依頼を出す機能、Hermes の API Server は使わない（下の「決めた理由」）
- 写真の元の大きさでの保存（縮小版だけでよい。ユーザーの回答）
- Hermes の内部の作業（SKILL.md の読み込み、curl のコマンド、ツールの結果、推論の文）の画面表示
- ひらがな・カタカナを区別しない検索（`docs/known-issues.md` の検索全般の課題として別に扱う）
- カレンダー・ダッシュボードへの表示

## してはいけないこと（できても失敗とみなす）

- サーバーの遮断（Hermes の実行ユーザーは Web 画面の5000番と `/opt/garden-app` に触れない）を崩すこと。アプリが `~/.hermes` を読む、アプリが Hermes に接続する、などの作りにしない
- `state.db` に書き込むこと。スクリプトは読み取り専用で開く（`mode=ro` の URI）。Hermes が動いている最中に読むので、ロックを長く持たない
- 送り直しでアプリ側の会話・発言・写真が二重になったり、前に届いた発言が消えたりすること（同じ会話は何度送っても同じ結果になる）
- `state.db` の構造が Hermes の更新で変わったとき、黙って壊れたデータを送ること（必要な列が無ければ送らずにエラーで止まる）
- 公開リポジトリに実環境の固有値（IP、ユーザー名、ホスト名）を書くこと

## 決めた理由（下調べの結果。2026-10-26）

下調べはサーバーの `state.db` と、サーバーと同じ版（`73162b00ee`）の Hermes のソースで行った。

- **API Server から取る案は採らない**: キーが1種類で権限を分けられず、履歴を読むためにアプリが持つキーで会話の削除や Hermes への依頼（ターミナルも使える）までできてしまう。アプリには認証が無い。API Server は「アプリから Hermes へ依頼を出す」機能を作るときに、その安全策と一緒に検討する
- **Hermes のプラグインのフックは使わない**: 1回のやりとりごとに呼ばれる `on_session_end` は会話の終わりではない。`on_session_finalize` は自動リセット（プラグイン `hermes-session-reset-policy`）でも呼ばれるが、リセットは次の発言が来たときなので、タイマーより早くならない。gateway の中で動くので、不具合が Hermes 本体に響く
- **写真は24時間で消える**: Hermes が受け取った写真は `~/.hermes/cache/images/` に置かれ、1時間ごとの掃除で24時間より古いものが消える（`gateway/run.py` の `_housekeeping_media_caches`）。そのためタイマーの間隔は24時間より十分短くする。既存の会話の写真はほとんど届かない

## state.db について分かっていること

- `sessions`: 1会話1行。`id`（例 `20261025_165529_f52993ca`）、`source`（`matrix` など）、`title`（全件にあった）、`started_at` / `ended_at` / `last_activity_at`（UNIX 秒の REAL）、`end_reason`（`session_reset` / `cli_close` / 空）、`parent_session_id`（リセットで続いた会話は前の会話を指す。圧縮の続きも同じ列を使い、そのときは親の `end_reason` が `compression`）、`message_count`
- `messages`: 1発言1行。`id`（連番）、`session_id`、`role`（`user` / `assistant` / `tool` / `session_meta`）、`content`、`tool_calls`（JSON の配列。`$[i].function.name` と `$[i].function.arguments`（JSON 文字列。terminal なら `{"command": "...", "timeout": 30}`））、`tool_call_id`、`tool_name`、`timestamp`、`display_kind`（失敗したやりとりは `failed_turn`）、`active` / `compacted`（圧縮で置き換えられた発言の印。2026-10-26 時点では圧縮の例なし）
- 写真付きの発言は `content` に `[Image attached at: /home/<user>/.hermes/cache/images/img_xxxx.jpg]` と `[screenshot]` の印が入る
- アプリの API は `terminal` の curl だけで呼ばれる（SKILL.md の指示）。コマンドは `curl -sS -H "Authorization: Bearer $GARDEN_API_TOKEN" "$GARDEN_API_URL/plantings/45"` のように環境変数のまま記録され、トークンの値は入らない。ツールの結果（`role='tool'`）は API の応答の JSON を含む
- ツールの使用回数（Matrix 以外も含む全体）: terminal 236、vision_analyze 31、skill_view 24 ほか

## 全体の流れ

```
[サーバー: Hermes の実行ユーザー]                    [サーバー: アプリ（garden）]
systemd ユーザータイマー（15分おき）
  → tools/hermes_conversation_sync.py
      state.db を読み取り専用で開く
      Matrix の会話のうち、前回から増えた・変わったもの
      写真の印があれば cache/images のファイル
  → POST $GARDEN_API_URL/conversations  ──────→  API（127.0.0.1:API_PORT）
                                                  会話・発言を Hermes の ID で上書き保存
                                                  写真は縮小版だけ保存
                                                  データとの結び付けを作り直す
                                                Web 画面（5000）: 一覧・詳細・各詳細画面の欄
```

## スクリプト（`tools/hermes_conversation_sync.py`）

- Python 標準ライブラリだけで書く（サーバーの `python3`。`tools/matrix_helper.py` と同じ方針）。サーバーの `~/` に置き、リポジトリの版をメイン PC から送る
- 接続先とトークンは `~/.config/garden-api.env`（`GARDEN_API_URL` / `GARDEN_API_TOKEN`）を読む。トークンは Hermes と同じものを使う（作る人の判断。スクリプトは Hermes と同じユーザーで動くので、別のトークンにしても Hermes から読めてしまい、分ける意味が薄い）
- 起動のたびに:
  1. `state.db` を `file:...?mode=ro` で開き、必要な列が `PRAGMA table_info` にあるか確かめる。無ければエラーを出して終了（何も送らない）
  2. `source='matrix'` の会話のうち、前回送ったときから発言が増えた・`title` などが変わったものを選ぶ（前回の状態は `~/.local/state/` などの小さな JSON に、会話ごとの最後の発言 ID などで持つ。状態のファイルが無ければ全件送る＝最初の取り込み）
  3. 会話ごとに1回 POST する。送るのは会話の項目と、その会話の発言（`session_meta` 以外の全 role。`tool` の `content` は terminal のものだけ、長いものは先頭を切り詰める。上限は作る人が決める。目安 20KB）。`reasoning` 系の列は送らない
  4. 発言の印にある写真のうち、まだ送っていないもの（状態のファイルで覚える）で、ファイルが残っているものを同じリクエストに multipart で付ける。消えていれば付けない
  5. 2xx が返った会話だけ状態のファイルを進める。失敗した会話は次の回にもう一度送る
- 途中の会話（まだリセットされていないもの）も送る。続きは次の回に同じ会話として送り、アプリ側で上書きされる
- ログは標準出力・標準エラーに出す（journal で見る）。トークンや発言の本文は出さない
- タイマー: ユーザーの systemd（`hermes-gateway.service` と同じく Hermes の実行ユーザー）。間隔は15分（作る人の判断。写真の24時間と、画面での新しさの釣り合い）。`Persistent=true`

## API（`POST /api/v1/conversations`）

- 既存の API と同じ認証・エラー形式・監査ログ。multipart の `data` パーツに JSON、写真は `images` パーツ（複数）。各写真のファイル名は印の `img_xxxx.jpg` のまま送り、アプリは発言中の印とファイル名で対応させる
- 会話は Hermes の会話 ID（`sessions.id`）で識別し、あれば上書き・無ければ作る（作成時 201、上書き時 200）
- 発言は Hermes の発言 ID（`messages.id`）で識別し、あれば上書き・無ければ追加する。**送られてこなかった発言は消さない**（Hermes 側で圧縮・削除されてもアプリには残す）
- 写真: 縮小版（既存の `make_thumbnail` と同じ 800×600 程度の JPEG）だけを `uploads/conversations/` に保存し、元のファイルは残さない。同じ会話の同じファイル名が既にあれば保存しない。GPS を外す・HEIC を変換する処理は既存の画像の保存と同じものを通す
- 応答には、保存した会話の ID、発言の件数、受け取った写真の件数を返す（スクリプトのログ用）
- 一覧・取得の `GET /conversations` は作らない（作る人の判断。Hermes に自分の会話を API で読ませる用途がまだ無い。必要になったら足す）
- `docs/api/README.md` に追加する。SKILL.md には書かない（Hermes に使わせるものではない）

## データとの結び付け（ユーザーと決めたこと）

アプリ側で、届いた発言から作り直す（会話を受け取るたびに、その会話の結び付けを全部作り直す。解析の誤りを直したら、全会話を作り直す手段も用意する。例: flask のコマンド）。

| 区分 | 拾い方 | 例 |
|---|---|---|
| 作った | `POST` の curl に対する応答（`role='tool'` で、呼び出しと `tool_call_id` が一致する発言）の `"data": {"id": N` | `POST /planting_records` → 312 |
| 変えた | `PATCH` の curl の URL の ID | `PATCH /plantings/45` |
| 見た | ID を指定した `GET`（`/{種類}/{id}` と `/{種類}/{id}/image`） | `GET /planting_records/312/image` |

- **一覧・検索（`GET /plantings?crop_id=1`、`/lookup` など）は「見た」に数えない**（ユーザーと決めた。1回の相談で何十件も結び付いて雑音になるため）
- 対象の種類は API の9リソース（作物・品種・場所・植え付け・栽培記録・収穫・料理・日記・タスク）と写真プール（`/photos`）。写真プールは詳細画面が無いので、結び付けは持つが表示は作る人の判断
- メソッドは curl の `-X` / `--request`、無ければ `-F` / `-d` / `--data*` があり `-G` が無いとき POST、それ以外は GET とみなす
- 1つのコマンドに複数の curl があるときは、URL ごとに拾う。応答の ID との対応が付けられない場合は「作った」を拾わない（取りこぼしは許容。ユーザーにも「拾えた分だけ」と伝えてある）
- 同じ会話で同じデータに複数の区分が付いたら、作った > 変えた > 見た の1つにまとめて表示する
- 消されたデータ（画面で削除した植え付けなど）への結び付けは、リンクを出さず「削除済み」と表示する
- 結び付けの解析は実データの例（上の「state.db について分かっていること」と、下のテスト）で確かめる

## 画面（Web、5000番）

- 一覧 `/conversations/`: 新しい順（最後の発言の時刻）。1行に日付、題名、件数（発言数）、写真の有無、結び付いたデータの件数。年・季節・月のバッジフィルター（`date-badge-filter.js`、日記・タスクと同じ）と、サーバーサイドのキーワード検索（題名と、ユーザー・Hermes の発言の文章）。ナビバーのメニューに追加する（位置は作る人の判断）
- 詳細 `/conversations/<id>`: 
  - 見出しに題名、始まり・最後の時刻
  - ユーザーの発言と Hermes の返事（`role` が `user` / `assistant` で文章のあるもの）を時刻順に、吹き出しなどで左右に分けて表示。返事は Markdown として表示（既存の `markdown` フィルター）。`failed_turn` の返事は「失敗したやりとり」と分かるようにする
  - 写真の印は本文から取り除き、届いた写真は縮小版を表示、届いていない写真は「写真あり（保存されていません）」
  - 「この会話で Hermes が作った・変えた・見たデータ」の一覧（区分ごと、各データの詳細へのリンク）
  - 前後の会話への移動（既存の `_detail_nav.html` と `get_adjacent()`）
  - リセットで続いた会話（`parent_session_id`）があれば「前の会話」へのリンク（作る人の判断）
- 各詳細画面（作物・品種・場所・植え付け・栽培記録・収穫・料理・日記・タスク）: 「このデータが出てきた Hermes との会話」の欄。日付・題名・区分（作った・変えた・見た）を新しい順に並べ、会話の詳細へリンク。結び付きが無ければ欄ごと出さない。共通部品にする
  - 作物の画面に品種経由のものまで含めるかは作る人の判断（目安: 含めない。その品種の画面で見られる）

## テーブル（目安。名前・列は作る人が決めてよい）

- `conversations`: Hermes の会話 ID（一意）、題名、`source`、始まり・終わり・最後の発言の時刻、終わり方、前の会話の Hermes ID、発言数、作成・更新時刻
- `conversation_messages`: 会話、Hermes の発言 ID（一意）、`role`、本文、ツール名、ツール呼び出し（JSON、terminal のみ）、時刻、`display_kind`
- `conversation_images`: 会話、元のファイル名（`img_xxxx.jpg`）、保存した縮小版のパス
- `conversation_links`: 会話、種類（`entity_type`）、ID、区分（作った・変えた・見た）、どの発言から拾ったか
- マイグレーションは `app/migrations/023_add_conversations.sql`。時刻は他のテーブルにそろえる（`state.db` は UNIX 秒なので変換する。表示は日本時間）

## 作る人に任せること（判断の目安つき）

- 状態のファイルの形と置き場所（目安: `~/.local/state/garden-conversation-sync.json`、600）
- ツールの結果の切り詰めの上限、1回の POST の大きさの上限（既存の API の 100MB・1枚20MB の範囲内）
- 一覧のページ分け（目安: 日記の一覧と同じ）
- 吹き出しの見た目（既存の Bootstrap と `custom.css` の範囲で）

## テスト

- API: 新規作成と上書き、同じ内容の送り直しで件数が変わらない、送られなかった発言が残る、写真の重複なし・縮小版だけ保存、認証なし 401、不正な JSON 422
- 結び付けの解析: 実データと同じ形の curl（`-G` と `--data-urlencode`、`-X PATCH`、`-F data=...`、`/image?size=thumb`、複数の curl）と応答から、作った・変えた・見たを正しく拾い、一覧・検索・`/lookup` は拾わない
- 画面: 一覧のキーワード検索、詳細で `tool` の発言や印が表示されない、各詳細画面の欄が出る／出ない
- スクリプト: テスト用の小さな `state.db`（必要な列だけのテーブル）を tmp に作り、API への送信を差し替えて、選ぶ会話・送る項目・状態のファイルの進み方・必要な列が無いときに止まることを確かめる（pytest から import できるようにする）

## サーバーへの配置（手順は文書に書く）

1. アプリの更新（いつもの手順。バックアップ → `git pull` → 再起動。マイグレーションが走る）
2. スクリプトをサーバーの `~/` に送り、まず手で1回動かす（最初の取り込み）。アプリの画面で12件が見えること、journal・アプリのログにエラーが無いことを確かめる
3. ユーザーの systemd のサービスとタイマーを置いて有効にする。Element X で依頼を1回送り、15分以内に一覧に出ることを確かめる
4. 写真付きの依頼を1回送り、縮小版が出ることを確かめる
