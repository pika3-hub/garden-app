# Hermes のアドバイスの保存と表示 設計

2026-10-27 にユーザーと決めた設計。wishlist の「Hermes のアドバイス（写真の診断など）を植え付けの画面で見られるようにする」の残り（案(2)）にあたる。

## 目的

ある野菜（作物・品種・植え付けが中心）について、過去に Hermes からどんなアドバイスを受けたかを、アプリの画面で振り返れるようにする。

- 作物・品種では植え付け前の相談（いつ植えるか等）、植え付けでは追肥の時期・生長のチェック・問題への相談などを振り返りたい
- 一番の使い道は「**Hermes に質問する前に、同じような質問を前にしていないかを自分で画面から確かめる**」こと（Hermes に「前に似た相談をしたか」を聞くことはない。聞くくらいなら質問そのものをする）

### 今あるものとの関係

2026-10-26 の会話の履歴（PR #87）（`/conversations/`、詳細画面の「Hermes との会話」の欄）は**会話（セッション）単位**で、見出しも会話に1つ。1つの会話で複数の相談をしたり話題が変わったりすると、目当ての相談を会話の中から探す必要がある。今回は**相談1件ずつ**の単位でアドバイスを保存する。会話の欄はそのまま残す。

## 目標と目標外

目標:
- Hermes が相談・質問に答えたら、そのアドバイスを自分で API に保存する。「保存して」と頼まれたときも保存する
- 植え付け・品種・作物の詳細画面に「Hermes のアドバイス」の欄を出す。品種・作物では配下の植え付け（作物では配下の品種も）の分もまとめて出す
- アドバイスの一覧画面（全件、キーワード検索）と詳細画面
- 画面からの手直し（見出し・相談・本文・日付・ひも付け先の編集、削除）

目標外（今回はしない）:
- 作業の依頼（「登録して」「写真を付けて」など）の保存。アドバイスではないので保存しない
- 「○○をメモしておいて」の保存先。これは補足情報のテキスト（wishlist の「外部 API で補足情報のテキストも登録・取得できるようにする」）として別に扱う。**先に本番で補足情報のテキストの利用実績を調べてから決める**（ユーザーの希望）
- 場所へのひも付け、カレンダー・ダッシュボードへの表示（Claude の判断。要れば後で足す）
- 画面からアドバイスを新しく作ること（Claude の判断。作るのは Hermes。画面は手直しだけ）

やってはいけないこと（アンチゴール）:
- Hermes が相談のたびに過去のアドバイスを持ち出して「前に追肥をすすめましたが、どうですか？」と聞くこと（ユーザーは余計だと感じる）
- 1つの話題のやりとりが、一覧で意味の分からない細切れ（「液肥でもいい？」だけの1件など）になること

## 1件のまとまり（ユーザーが決めた軸）

- **同じ会話の中で同じ話題が続いている間は1件**にまとめ、Hermes が更新（PATCH）で書き足して整理する
  - 例: 「2回目の追肥はいつ？」→「量は？」→「液肥でもいい？」は1件（見出し「2回目の追肥（時期・量・液肥）」）
- 話題が変わったら、時間的に続いていても**別の1件**
- 別の会話で同じ話題をまた聞いたときも**別の1件**（時期が違えば株の状態も答えも違うため）

## データ

新しい表を作る（補足情報 `supplements` は1件が1つのデータにしか付かず、植え付けにも付けられないため使わない）。名前は Claude の判断。

`advices`
| 列 | 型 | 内容 |
|---|---|---|
| id | INTEGER PK | |
| title | VARCHAR(200) NOT NULL | 相談の見出し（例: 2回目の追肥はいつ？） |
| question | TEXT | ユーザーが相談したことの要約 |
| answer | TEXT NOT NULL | アドバイスの本文（Markdown） |
| advised_on | DATE NOT NULL | 相談した日 |
| created_at / updated_at | TIMESTAMP | 既存の表と同じ JST の既定値 |

`advice_relations`（既存の `task_relations` と同じ形）
- `advice_id`、`relation_type`（`crop` / `variety` / `location_crop`）、`crop_id` / `variety_id` / `location_crop_id`。FK と ON DELETE CASCADE は既存の関連表に合わせて書くが、**アプリは `PRAGMA foreign_keys` を有効にしていないので CASCADE は動かない**（`get_db()` は ON にしていない。アプリ全体で有効にするのは今回しない）。そのため:
  - アドバイスの削除では、モデルで `advice_relations` を明示的に消す（`Task` などの `save_relations` / 削除と同じ）
  - 作物・品種・植え付けを消したあとに残る関連の行（孤児）は、集約・表示・編集モーダルで参照先と JOIN して自然に除く（既存の日記・タスクの関連と同じ扱い）
  - 品種を消したときは、その品種への関連を**親作物への関連に付け替える**（植え付けの昇格トリガー `trg_promote_variety_plantings_before_delete` と同じ考え方。`advice_relations` 用の BEFORE DELETE トリガーを足す。トリガーは FK の設定と関係なく動く）。Claude の判断
- 1件のアドバイスに複数のひも付け先を持てる。ひも付け先が無いアドバイス（特定の野菜に関係しない一般的な相談）も許す（一覧画面にだけ出る）
- ひも付けの使い分け（SKILL.md で Hermes に指示する）: 植え付けについての相談は**植え付け**、植え付け前の品種・作物についての相談は**品種／作物**。上位への集約は画面側で行うので、植え付けの相談を品種・作物にも重ねて付けない

マイグレーションは次の連番（`024_...`）。`schema.sql` は初期の表しか持たない慣習なので触らない。`app/models/CLAUDE.md` は更新する。

### 集約のルール（詳細画面の欄・API の絞り込み共通）

- 植え付け X: `location_crop_id = X` のアドバイス
- 品種 V: `variety_id = V`、または品種 V として植えた植え付け（`plantings.variety_id = V`）にひも付いたアドバイス
- 作物 C: `crop_id = C`、または親が C の品種、または作物 C の植え付け（品種経由を含む。`crop_variety_view` の `effective_crop_id = C`。`_CV_JOIN` を使う）にひも付いたアドバイス
- 重複は1件にまとめる。並びは `advised_on` の新しい順、同じ日は id の新しい順

### 元の会話とのつながり

アドバイスに会話の ID は持たせない。会話の履歴の取り込み（`tools/hermes_conversation_sync.py` → `app/utils/conversation_links.py`）は、Hermes の curl の `POST` / `PATCH` から作った・変えたデータを `conversation_links` に記録している。`RESOURCE_TYPES` に `'advices': 'advice'` を足せば、アドバイスと元の会話は自動で結び付く（Hermes が自分のセッション ID を知る必要がない）。

- 結び付くのは次の取り込み（15分おき）の後。それまで「元の会話」のリンクは出ない（許容）
- 反映後に `uv run flask --app app relink-conversations` を本番で1回実行（既存の会話に影響はないが、手順として）
- アドバイスの詳細画面に既存の `_hermes_conversations_section.html`（`hermes_conversations('advice', id)`）を出し、これを「元の会話」とする。ただし**作った（created）・変えた（updated）会話だけ**に絞る（後の会話で Hermes が `GET /advices/{id}` で読んだだけの会話は「元の会話」ではないため）。共通部品・グローバル関数に kind の絞り込みを足すか、アドバイス用に絞って渡す。Claude の判断。欄の中で開いたアドバイスからも元の会話へリンクする（最初の `created` の会話）
- 会話の詳細画面の「作った・変えたデータ」のリンクにアドバイスも出るよう、種類名・URL の対応表に `advice` を足す

## API（`/api/v1/advices`）

既存の `Resource` 基底クラス＋`RelationsMixin`（タスクと同じ作り）。削除なし。

- `GET /advices`（一覧）、`GET /advices/{id}`、`POST /advices`、`PATCH /advices/{id}`
- 項目: `title`（必須、200字まで）、`question`、`answer`（必須）、`advised_on`（`YYYY-MM-DD`。省略時は今日）、`relations`（`crop_ids` / `variety_ids` / `planting_ids`）
- 絞り込み: `q`（`title` / `question` / `answer` のキーワード）、`date_from` / `date_to`（`advised_on`）、`crop_id` / `variety_id` / `planting_id`（上の「集約のルール」と同じ範囲）
- 補足情報・画像は無し
- `docs/api/README.md` に節を足す。`GET /meta` に種類の一覧などがあれば合わせる

## 画面

ユーザーが見本の **A**（アドバイス欄を別に作り、会話の欄はその下に残す）を選んだ。

### 詳細画面の「Hermes のアドバイス」の欄（共通部品）

- 植え付け・品種・作物の詳細画面に出す。位置は「Hermes との会話」の欄の**すぐ上**。0件なら欄ごと出さない（会話の欄と同じ）
- 見出しに件数のバッジ。欄の中に絞り込みの入力欄（クライアントサイド。見出し・相談・本文の文字で絞る）
- アコーディオン: 閉じた状態で見出しと「日付・（品種・作物の画面では）どこで受けたか」の印（例: 「植え付け: 南の畑」「品種: アイコ」）。開くと「相談」「アドバイス」（Markdown 表示。`markdown` フィルター）と「元の会話を見る」「詳細」へのリンク
- 最初の1件を開いておくかは Claude の判断（開いておかない。件数が多いと縦に長くなるため）
- 共通部品として作る（例: `_hermes_advice_section.html` ＋ Jinja グローバル）。会話の欄（`_hermes_conversations_section.html` / `hermes_conversations`）と同じ呼び方に揃える

### 一覧・詳細・編集（`/advices/`）

- 一覧: 新しい順。サーバーサイドのキーワード検索（日記と同じ）、年・季節・月のバッジフィルター（`date-badge-filter.js`）。各行は見出し・日付・ひも付け先・本文の冒頭（プレーンテキスト）
- 詳細: 見出し・日付・ひも付け先（各詳細画面へのリンク）・相談・アドバイス（Markdown）・「Hermes との会話」の欄。前後移動（`_detail_nav.html` と `get_adjacent()`）、編集・削除ボタン
- 編集: 見出し・日付・相談・アドバイス・ひも付け先（`entity-select-modal.js` のカード型モーダル。作物・品種・植え付け）。新規作成のフォームは作らない
- 削除: 確認のうえ物理削除（ひも付けはモデルで一緒に消す。上の「データ」を参照）
- メニュー: ナビの「Hermes」（会話の履歴）の近くから行けるようにする。置き方（ドロップダウンにするか、会話の一覧にタブ・リンクを置くか）は Claude の判断で、既存のナビの作りに合わせる

## Hermes（`docs/api/hermes-skill/SKILL.md`）

「相談・アドバイスの保存」の節を足し、次を指示する。

- 保存するとき: ユーザーの相談・質問に答えたとき（栽培の相談、生育の診断、問題への対処、時期の質問など）。「保存して」と頼まれたときも
- 保存しないとき: 作業の依頼（登録・更新・写真の添付など）への返答、あいさつや雑談
- 1件のまとまり: 同じ会話で同じ話題が続く間は、最初に作ったアドバイスを `PATCH` で更新する（見出し・相談・本文を、それまでのやりとり全体を整理した内容に書き直す）。更新の前に `GET /advices/{id}` で今の内容を読み、それを元に書き足す（ユーザーが画面で手直しした内容を上書きで消さないため。Claude の判断）。話題が変わったら新しく `POST`。別の会話では常に新しく作る
- アドバイスの保存・更新は、他の `PATCH` と違って**事前の確認をしない**（毎回確認されると相談の流れを邪魔するため。「守ること」の「PATCH の前に確認する」の例外として明記）
- 書き方: `title` は相談の中身が一覧で分かる短い見出し、`question` はユーザーが聞いたことの要約、`answer` は答えた内容を Markdown で整理（返答の丸写しではなく、あとで読んで分かる形）。`advised_on` は `date +%F` の今日
- ひも付け: 上の「ひも付けの使い分け」のとおり。対象が特定できない一般的な相談はひも付けなしで保存してよい
- 保存したことは返答の最後に短く添える（例: 「（アドバイスとして保存しました）」）。Claude の判断
- 過去のアドバイスを読むのは、質問に答えるのに必要なときだけ（`GET /advices?planting_id=...` など）。毎回読んで過去の提案のその後を聞いたりしない
- 「生育状況の診断」の「診断の結果は、頼まれない限り記録や日記に書き込まない」は、「記録や日記には書き込まない（栽培記録のメモを頼まれたときを除く）。アドバイスとして保存する」に改める

SKILL.md はサーバーへ送り、Element X で `/new` してから試す。

## 確かめ方

- テスト（pytest）: マイグレーション、モデルの集約（作物・品種・植え付けの範囲、品種経由、重複の除去）、API（作成・更新・絞り込み・不正な値）、画面（一覧・詳細・編集・削除、各詳細画面の欄）、`conversation_links` が `/advices` の POST・PATCH を拾うこと
- ブラウザ: コピー DB で植え付け・品種・作物の詳細画面の欄、絞り込み、一覧の検索
- 本番（PR のブランチで）: Element X で実際に相談し、(1) 保存される (2) 同じ話題の続きで同じ1件が更新される (3) 話題を変えると別の1件になる (4) 作業の依頼では保存されない (5) 15分後に元の会話が結び付く、を確かめてからマージ

## 作る側に任せること

- 表・ファイル・関数・テンプレートの具体的な名前（上の名前は案）
- 欄・一覧の細かい見た目（既存の会話の欄・日記の一覧に合わせる）
- 一覧の本文の冒頭の文字数など
