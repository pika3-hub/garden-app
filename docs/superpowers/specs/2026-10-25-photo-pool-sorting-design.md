# 写真プールの振り分け画面 設計

- 作成: 2026-10-25
- 対応する wishlist: 「写真プールの写真を AI に振り分けてもらい、承認して一括登録する」（段階4）

## 目的と背景

写真プールには、前日〜当日にまとめて撮った写真が数枚から多いときで30枚ほど入る。用途は栽培記録が最も多く、次に収穫、その次に日記・料理。写真プールへのアップロードはスマホ、振り分けて登録するのはおもに PC。

今は写真プールから1枚ずつ各登録画面に移り、入力して保存すると、それぞれの画面の移動先（一覧・詳細・見取り図の配置など）に飛ばされる。そのたびにメニューから写真プールへ戻って続きを登録する、という**行き来が一番の負担**。

そこで、写真プールで選んだ写真を**1つの画面で1枚ずつ大きく見ながら、種類と対象を選んで登録し、「保存して次へ」で次の写真に進む**画面を作る。AI は、人が種類と対象を選んだあと、ボタンを押したときだけ、種類ごとに決まった一部の項目（メモなど）を下書きする補助役にとどめる。

当初の wishlist の案（AI が写真ごとに種類・対象まで提案する）は採らない。ユーザーは写真を見れば対象がすぐ分かる一方、AI には畑・場所の見分けが難しく、間違えられる方が困るため。

## ゴール

- 写真プールで複数枚を選び、振り分け画面で1枚ずつ登録して、最後まで写真プールに戻らずに済む
- 1枚ごとに次の種類で登録できる: 作物、品種、場所、植え付け（＋栽培記録）、栽培記録、収穫、料理、日記
- 栽培記録・収穫は、1枚の写真に対して**植え付けを複数選べる**（選んだ数だけ記録ができ、どれにも同じ写真が付く）
- 「✨ AIで下書き」ボタンで、種類ごとに決まった項目を AI が写真を見て下書きする。人が確認・修正してから保存する
- 記録日は写真の撮影日を初期値にする
- たまにある「同じ写真を2つの行き先に登録したい」ときのため、保存後に同じ写真で続けて登録できる
- 写真プール一覧で、写真ごとに**使用先（登録したデータ）へのリンク**を出す。「この写真をどこに登録したっけ」をすぐ確かめられるようにする

## やらないこと（今回）

- AI に種類・対象（どの植え付けか）を推定させること
- AI の下書きを自動で始めること（ボタンを押したときだけ。補助が不要な写真もあるため）
- 補足情報（追加画像）を行き先にすること（wishlist に残す）
- 栽培記録・植え付けに補足情報を付けられるようにすること（孫のデータになり参照しづらいため。1枚ずつ別の栽培記録にする）
- 使い終わった写真を写真プールから削除する機能（写真はそのまま残し、今と同じく使用回数が増えるだけ）
- 収穫量を AI に数えさせること（人が入れる。要望があれば後で足す）
- 前回の栽培記録の**写真**を AI に送ること（送るのはメモの文章だけ。画像が倍になり料金が増えるため）
- 外部 API（`app/api/`）・Hermes（`SKILL.md`）の変更

## してはいけないこと（できても失敗とみなす）

- AI が人の確認なしに保存すること。AI は入力欄に下書きを入れるだけで、保存は必ず人が押す
- 栽培記録のメモにアドバイスを書くこと。栽培記録は観察の記録で、アドバイスの置き場所は別にしたい（段階5 で検討）
- 既存の流れを壊すこと: 写真プールの1枚ずつの「登録先を選ぶ」モーダル（`/photo_pool/<id>/use`）、各画面の「写真プールから選択」、まとめて登録（`/plantings/bulk/new`、`/harvests/bulk/new`）はそのまま使える状態を保つ

## 画面の流れ（ユーザーと決めたこと）

1. 写真プール一覧（`/photo_pool/`）で写真を選ぶ。既存の選択バー（チェックボックス・「表示中を全選択」・一括削除）に「選んだ写真を振り分ける」ボタンを足す
2. 振り分け画面に移る。モックアップの B 案: 上に選んだ写真のサムネイル列（済・現在・未の表示）、中央に写真を大きく、その下に入力欄
3. 写真ごとに:
   1. **人が種類を選ぶ**（作物／品種／場所／植え付け＋栽培記録／栽培記録／収穫／料理／日記）。種類に応じて入力欄が切り替わる
   2. **人が対象・必須項目を入れる**（下の表）
   3. 必要なら「✨ AIで下書き」を押す → AI が写真と文脈を見て、その種類の担当項目を入力欄に入れる
   4. 人が確認・修正して「保存して次へ」。保存したら同じ画面で次の写真へ進む（各機能のふだんの移動先・見取り図の配置画面には移らない）
   5. 同じ写真を別の行き先にも登録したいときは「保存して、この写真で続けて登録」。保存後も同じ写真のまま、種類の選択からやり直せる（この写真で登録済みのものを一覧で見せる）
   6. 登録しない写真は「スキップ」
4. 最後の写真を終えたら写真プール一覧に戻り、登録した件数を表示する
5. 途中でやめても、保存した分は残る

## 種類ごとの入力項目と AI の担当（ユーザーと決めたこと）

| 種類 | 人が入れる | AI が下書きする項目 | 作られるデータ |
|---|---|---|---|
| 作物 | 名前・種類（`crop_type`）など既存フォームの項目 | メモ（既存の AI メモ下書きと同じ。名前と地域から書く。写真は使わない） | 作物1件（画像＝この写真） |
| 品種 | 親の作物・名前など | メモ（同上） | 品種1件（画像＝この写真） |
| 場所 | 名前など | メモ（写真に写った場所の様子） | 場所1件（画像＝この写真） |
| 植え付け＋栽培記録 | 作物か品種・場所・植え付け日など既存の植え付けフォームの項目 | 栽培記録のメモ（植え付け時の様子） | 植え付け1件（位置は未設定。配置は後で見取り図から）＋その植え付けの栽培記録1件（画像＝この写真、記録日＝植え付け日） |
| 栽培記録 | 対象の植え付け（**複数可**）・記録日 | メモ（写真の様子と、前回の栽培記録からの変化。アドバイスは書かない） | 選んだ植え付けごとに栽培記録1件。メモは全件共通 |
| 収穫 | 対象の植え付け（**複数可**）・収穫日・植え付けごとの収穫量と単位 | メモ（実の様子など） | 選んだ植え付けごとに収穫1件。メモは全件共通、収穫量・単位は植え付けごと |
| 料理 | 調理日・関連（作物・品種・植え付け・収穫） | タイトル・カテゴリ・メモ | 料理1件（画像＝この写真） |
| 日記 | 日付・関連（作物・品種・場所・植え付け・収穫） | タイトル・本文 | 日記1件（画像＝この写真） |

補足:
- 植え付けには画像の項目が無い（一覧などに出る画像は最新の栽培記録の画像）。そのため「植え付け」を選んだときは最初の栽培記録を一緒に作り、写真はそちらに付ける
- 日付の初期値は写真の撮影日（`photo_pool.taken_at` の日付部分）。無ければ今日。人が直せる
- 「前回の栽培記録」は、対象の植え付けごとに、記録日がこの写真の記録日より前で最新の栽培記録のメモ。植え付けを複数選んだときは、それぞれの前回のメモを渡し、共通のメモ1つにまとめて書かせる
- 振り分けの途中で作った作物・品種・場所・植え付けは、続く写真の選択肢に出る

## 写真プールの使用先リンク（ユーザーと決めたこと）

- 写真プール一覧の各写真に、使用先の一覧（種類と名前、例:「栽培記録 ミニトマト（アイコ）2026-10-25」）を出し、それぞれの詳細画面へ移れるようにする
- 元にするのは `photo_pool_usages`（`entity_type`, `entity_id`）。記録されている種類は `crop` / `variety` / `location` / `planting_record` / `harvest` / `cooking` / `diary` / `supplement`（Web の各画面と API の両方が記録している）
- `supplement` は補足情報そのものに詳細画面が無いので、`supplements.entity_type` / `entity_id` を辿って親（作物・日記など）の詳細画面へ移る
- 使用先のデータが削除済みのとき（使用の記録は残る）は、リンクにせず「削除済み」と出す（作る人の判断。`usage_count` が削除済みも数えている今の挙動は変えない）
- 見せ方（写真の下に折りたたみで出す、写真を押したモーダルに出す、など）は作る人に任せる。写真の数が多くても一覧が重くならないこと（1枚ごとに問い合わせない）

## 技術的な前提（コードから確かめたこと）

- 写真プール: `photo_pool`（`image_path`、`taken_at` は EXIF から）、使用記録は `PhotoPool.record_usage(photo_id, entity_type, entity_id, copied_image_path)`。各エンティティへの写真は `copy_image(src, folder)` で**行ごとに独立したコピー**を作る（同じファイルを複数行で共有すると片方の削除で壊れるため。`harvest_routes.bulk_create` 参照）
- 複数の植え付けの選択は、まとめて登録で使っている `_build_planting_multi_select_data()`（`planting_routes.py` / `harvest_routes.py`）とその選択モーダルを使い回せる
- 料理・日記の関連付けは `entity-select-modal.js` を使い回せる
- 料理のカテゴリの候補は `Cooking.get_categories()`
- AI 呼び出しは `app/utils/ai_notes.py`（モデルは `current_model()`＝`.env` の `ANTHROPIC_MODEL`、本番は Haiku 5.5。キー未設定時は `is_available()` が偽）。作物・品種のメモは既存の `/settings/ai/notes-draft` と `ai-notes.js` をそのまま使う
- 植え付けの作成は `Planting.plant(data)`。ふだんの `plant_create` は見取り図の配置（`plantings.place`）に移るが、この画面では移らない

## 作る人に任せること（判断の目安つき）

- **画面の作り方**: サーバー側で1枚ずつ描画してフォームを POST し、保存後に次の写真へリダイレクトする形がこのアプリの他の画面と揃う（AI 下書きのボタンだけ fetch）。選んだ写真の一覧と済みの写真は URL のパラメーターで持てば足りる（途中で再読み込みしても、保存済みのデータは消えない）。単一ページの JS にするなら、その理由を計画に書く
- **写真の並び順**: 撮影日時の古い順（無いものは写真プールへの登録順）
- **入力エラー時**: 同じ写真の画面に入力値を残して戻す（まとめて登録の `rows_values` の作りが参考になる）
- **AI 下書きの実装**: `ai_notes.py` の呼び出し・エラー処理（`AiNotesError`、タイムアウト、メッセージ）を再利用し、写真用の関数を足す（ファイルを分けるかは任せる）。送る画像は写真プールのサムネイル（800×600 JPEG）。Web 検索は使わない。返り値は種類ごとの項目を JSON で受け取り、入力欄に入れる。プロンプトには「観察だけを書き、アドバイスは書かない」「写真から分からないことは書かない」を入れる。料理のカテゴリは既存の候補から選ばせ、合わなければ新しい名前でもよい
- **AI が使えないとき**（キー未設定）: ボタンを出さないか無効にする。既存の AI メモ下書きのボタンの扱いに合わせる
- **既存フォームの部品の使い回し方**: 各機能の form.html から入力欄を include で切り出すか、振り分け画面用に書くか。既存フォームの見た目・項目と食い違わないこと
- スマホ幅でも崩れないこと（主な利用は PC）

## テスト

- 種類ごとに、保存で正しいデータができ、写真が独立したコピーとして付き、`photo_pool_usages` に記録されること
- 栽培記録・収穫で植え付けを複数選んだとき、件数・共通メモ・植え付けごとの収穫量
- 植え付け＋栽培記録で、植え付けと栽培記録が1件ずつでき、記録日が植え付け日になること
- 保存後に次の写真へ進み、最後は写真プールに戻ること。スキップ。「この写真で続けて登録」で同じ写真に留まること
- 写真プール一覧の使用先リンク: 種類ごとの移動先、補足情報は親へ、削除済みの扱い
- 入力エラー時に入力値が残ること
- AI 下書き: フェイククライアントで、種類ごとの返り値・前回の栽培記録のメモが渡ること・キー未設定時の扱い（実 API は呼ばない）
- 既存の写真プール・まとめて登録のテストが通ること
